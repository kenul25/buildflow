# Member 01 construction API

Apply the EF Core `Member01Construction` migration to PostgreSQL with `dotnet ef database update`. The API already uses `ConnectionStrings:DefaultConnection`. Configure `Planning:BaseUrl` as the loopback URL of the Python service and `Planning:InternalKey` through ASP.NET Core user secrets or an environment variable such as `Planning__InternalKey`. Set the same value as `BUILDFLOW_INTERNAL_KEY` for Python. Keep the Python listener on loopback or a private network.

## Routes

`GET/POST /api/projects`, `/api/sites`, `/api/phases`, `/api/activities`; `GET/PUT/DELETE /api/{collection}/{id}`. DELETE archives. Read routes require JWT; write and archive routes require ProjectManager or Administrator. SiteEngineer reads are limited to assigned projects and descendants. List query supports `search`, `status` (projects and activities), `parentId`, `sort=name|updatedAt|createdAt`, `desc`, `page`, `pageSize` (1–100), and `includeArchived`.

`POST /api/construction/activities/{id}/progress` adds an append-only update. `GET` at the same path returns history. Progress cannot decrease. `POST /api/construction/activities/{id}/photos` accepts multipart `file` with a verified JPEG, PNG, or WebP up to 5 MB; `GET /api/construction/photos/{id}` authorizes before serving it. Store uploaded files on durable private storage in production, with backups matching the database.

`POST /api/construction/resource-requests` requires a project, site, activity, objective and 1–50 resource items. `GET /api/construction/resource-requests` returns the user's visible requests and workflow status. `POST /api/construction/resource-requests/{id}/planning` creates one workflow for a request and calls the internal planner; `GET /api/construction/planning-workflows/{id}` returns its status and structured plan. A failed planner call is persisted as `Failed`. Starting a nonfailed workflow returns the existing record; starting a failed one retries planning.

The Site Engineer can update or request only within an assigned, active project. ProjectManager and Administrator have broader access. Audit timestamps are set in `BuildFlowDbContext`; construction writes also record actor IDs.

## Planner integration

`POST /internal/plans` is a private FastAPI JSON endpoint secured with `X-BuildFlow-Key`. It accepts `workflowId`, `requestId`, `projectId`, `siteId`, `activityId` (UUID strings), `objective`, optional project/site/activity names and site address, optional `requiredBy` ISO date and `budgetLimit`, and `items` each with `kind` (`Material|Equipment|Workforce`), `name`, positive `quantity`, `unit`. It returns schema version `1.0`, `AwaitingAgents`, a constraint analysis, numbered execution `steps`, and ordered `tasks`. The response also includes `executionSummary` with Planning Agent identity, model name, accepted generated plan, validation result, timing, retries, safe errors, node events, and final planning status. Failed calls store a safe summary in the existing `PlanningWorkflow.PlanJson` column; retrying a failed workflow preserves previous summaries in `executionHistory`.

Each task has `task_id` (UUID), `agent`, `action`, `depends_on` (task IDs), `input`, and `status=Pending`. Gemini proposes only the allow-listed `InventoryAnalysisAgent`, `ProcurementAgent`, and `SchedulingValidationAgent` tasks. Trusted Python code maps `InventoryAnalysisAgent` to the existing version 1.0 wire name `InventoryAgent` and creates all task IDs, inputs, and dependencies. The ASP.NET planner request now includes a read-only `inventorySnapshot` containing material name, unit, current stock, and reserved stock; trusted task materialization passes it to the Inventory task. The Inventory agent aggregates duplicate warehouse records, reports exact shortages, and performs no reservations or stock mutations. Procurement depends on its shortage output; SchedulingValidation depends on both. The `AgentPort.execute(task)` protocol is the integration point for the other members. Their JSON response contains `schemaVersion=1.0`, `task_id`, `agent`, `status=Completed|Failed`, `output` as a structured object and optional `error`. Agents submit it to `POST /api/construction/planning-workflows/{id}/agent-results` with `X-BuildFlow-Key`. The endpoint checks task identity and dependencies, stores the output and moves to `AwaitingBackendValidation` when all three report completion. The final scheduling output must be checked by deterministic backend rules before any manager approval state. No stock reservation, purchase order, worker assignment, or equipment reservation is performed by Member 01.

State progression: `Queued → AwaitingAgents → AwaitingBackendValidation → PendingProjectManagerApproval → Approved|Rejected|RevisionRequested`; `Failed` may be entered from planning or agent execution. Member 01 persists agent task results inside the structured plan. Later members must add deterministic validation and approval actions before enabling subsequent transitions. No hidden reasoning is stored.

The Python service reads `GEMINI_API_KEY` and `GEMINI_MODEL=gemini-3.5-flash-lite` only from its server environment. Its LangGraph workflow uses bounded model retries and deterministic Pydantic and business-rule checks before accepting a proposal. Gemini receives validated request context only and no tools. See `backend/agentic-ai/ADR-001-llm-planning.md` for the architecture decision and `backend/agentic-ai/README.md` for setup.
